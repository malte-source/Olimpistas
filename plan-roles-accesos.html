Roles y accesos:
cada uno ve lo suyo

Hoy toda clave de admin da acceso total. A medida que sumás gente (marketing, finanzas, soporte), conviene que cada uno entre con su clave y vea solo lo que le toca. Este plan define los roles entendiendo qué hace realmente el sistema.

🎯 Qué es este sistema (para diseñar bien los accesos): Olimpistas.com es el embudo mundial de hinchas de Club Olimpia. El admin gestiona: socios (la base), pagos (conciliación Metrepay + membresías Plus/Junior), campañas de remarketing (→ GoHighLevel), contenido (sorteos, preventas, media), el padrón oficial de socios, moderación de selfies, reportes de negocio y sistema (salud, auditoría, claves). Son tareas de equipos distintos → tiene sentido separarlas por rol.

👥 Los 5 roles

Pensados por "trabajo a hacer", no por jerarquía.

owner

Dueño / Dev

Acceso total, incluido Sistema (salud, auditoría, claves, flags). Es vos. Es el rol por defecto si una clave no especifica rol.

finanzas

Finanzas / Administración

Concilia pagos Metrepay, cuadre, activa/da de baja membresías y exporta CSV contable. No toca contenido ni campañas.

marketing

Marketing / Contenido

Crea sorteos, preventas y contenido; lanza campañas y mide conversión; arma segmentos y los empuja a GHL. No toca la plata.

soporte

Soporte / Comunidad

Busca socios, edita fichas, reenvía verificación, modera selfies y resuelve la cola del padrón. El día a día con el hincha.

lectura

Directivo / Lectura

Ve el dashboard y los reportes. No puede modificar nada. Ideal para mostrar números sin riesgo.

⚙️ Cómo se implementa

Encima del sistema multi-clave que ya existe — cambio chico y no rompe nada.

1

Rol en la clave

Extender el formato de ADMIN_KEYS a nombre:clave:rol (ej. marce:xxxx:marketing). Si no se pone rol, default owner → las claves de hoy siguen con acceso total. Cero migración forzada.

2

Permisos en el server (la seguridad de verdad)

El middleware lee el rol y una matriz de permisos protege cada grupo de endpoints. Esto es lo que realmente bloquea — no alcanza con esconder botones.

3

La interfaz se adapta (UX)

Un endpoint /admin/whoami devuelve el rol; el panel oculta las áreas y botones que ese rol no puede usar. Es comodidad visual; la barrera real es el paso 2.

4

Auditoría por rol

El log ya registra quién (por: nombre); se le suma el rol. Trazabilidad completa de quién tocó qué.

⚠️ Regla de oro: esconder botones en el navegador no es seguridad — cualquiera con la clave podría llamar la API igual. La protección real va en el servidor (paso 2). Lo del frontend es solo para que cada uno vea una pantalla limpia con lo suyo.
✅ No rompe nada: se construye sobre el ADMIN_KEYS que ya funciona. Las claves actuales quedan como owner (acceso total) hasta que les asignes un rol. Se puede hacer gradual: primero ocultar áreas en la UI, después endurecer el server.

🚀 A futuro (opcional)

Si el equipo crece mucho: pasar de "claves compartidas" a cuentas reales (usuario + contraseña con sesión), gestión de altas/bajas desde el propio panel, y 2FA para owner. Es un salto más grande; no hace falta para arrancar con roles.

Recomendación de arranque: implementar pasos 1–3 (rol en la clave + permisos en server + UI adaptada) para los 3 perfiles que más se usan: owner, marketing y finanzas. El resto se suma cuando haga falta.
